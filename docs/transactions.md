# Repair transactions

Only hosts cleanup is enabled in this release. It removes Claude/Anthropic domain aliases, preserves unrelated aliases and comments, and is covered by an end-to-end fake-adapter test. Other typed operations are reserved for future providers and are rejected by the helper. `EnvironmentCheck` remains read-only; repair providers produce `FixPlan` values separately.

The UI requests an opaque plan ID and redacted preview, then asks for confirmation. Plans are retained in a bounded server-side map, consumed once, and checked against current unredacted resource values before execution. The UI cannot submit executable steps. New providers must register resources, supply accurate previews, implement typed snapshot/restore operations, and extend helper validation explicitly.

`SystemAdapter` separates reads from privileged writes. The executor obtains an in-process resource lock and an OS file lock under the app data directory. The file lock conservatively serializes transactions across app instances and releases on process exit. It snapshots every resource and atomically persists a versioned backup before sending one batch to the helper. Backups are private JSON files in `app_data_dir()/backups/`; canonical JSON recursively sorts object keys. SHA-256 is calculated with the `sha256` field blank. `sha2` 0.10.9 was available in the offline cache. Integrity detects corruption; it is not a cryptographic signature proving who authored a backup.

A batch applies steps in order and undoes successful steps in reverse order on failure, including a best-effort undo of the failing step (writes can fail after partially changing state). Reports distinguish applied, failed, rolled_back, rollback_failed, and skipped steps. Backup files remain available after failed transactions. Failed rollback requires manual recovery from that backup. Restore uses the same executor with a separate recovery snapshot under `recovery/`, excluded from backup history so repeated “Restore everything” does not toggle states. Restore everything verifies all historical backups first, applies them newest first in a single elevated batch, and rolls the whole batch back on failure.

Linux launches `pkexec`; only when it is unavailable does it try `sudo -n`, which cannot prompt for a terminal password. macOS uses an AppleScript administrator prompt; Windows uses PowerShell `Start-Process -Verb RunAs -Wait`. Each launches the same binary with `--helper <request-file> <sha256>`, before Tauri initialization. The digest is passed separately as an argument and binds the helper to the exact bytes prepared by the parent. The helper checks schema, operation types, exact allowlisted paths, snapshot scope, and current values before writing. It rejects command, registry, DNS, and timezone operations today. A digest-bound result file returns the step statuses. The parent precreates the private output file; the helper opens it without creation or truncation and checks its identity/ownership on Unix or rejects reparse points on Windows before writing through that handle. No UI-supplied shell strings are evaluated. Request files are private and removed after completion; result files contain statuses only.

After a transaction returns, Tauri runs a full fresh scan, collecting a new platform snapshot and constructing a new `ScanContext`; no cached context is reused. This also refreshes checks that might depend indirectly on the edited resource. A scan failure is returned separately from the transaction report.

Tests exercise only fake adapters and temporary directories. Native authorization dialogs, packaged helper launch, and actual system writes require platform smoke tests and have not been executed by this feature's tests.
